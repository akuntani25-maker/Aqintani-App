# RCA — run 716da2ae-5412-4a79-a98b-2dfdcc6686cc (partial-payment-dev)

## Verdict
Deploy failed at `deploy_k8s` (readiness timeout). This is an **application startup hang**, NOT a manifest/infra problem. The FastAPI `@app.on_event("startup")` hook runs a heavy per-record data-migration loop against the **production** MongoDB that takes longer than the readiness window, so uvicorn never finishes startup and never binds port 8001. nginx then returns `connect() failed (111: Connection refused)` to `/health` for 10 minutes until the rollout times out.

## Evidence
- Pod logs (failed run), in order:
  - `Starting FastAPI backend: uvicorn server:app --host 0.0.0.0 --port 8001`
  - `Emergent object storage initialized`
  - `Database indexes created successfully` (03:21:03)
  - …then **no** `Application startup complete` / `Uvicorn running on 0.0.0.0:8001` line — startup never finished.
  - `WARNING: Backend did not respond within 120s, but process is running - continuing`
  - Continuous nginx `connect() failed (111: Connection refused) ... upstream http://127.0.0.1:8001/health` until rollout timeout at 03:25:42.
- Uvicorn runs the lifespan/startup hook **before** opening the listen socket, so a slow startup hook = refused connections (exactly what nginx shows), not a crash.
- Manifest chain is correct: entrypoint starts `uvicorn ... --port 8001`, nginx proxies `/health`→`127.0.0.1:8001`. No manifest fault.

## Why it blocks (quantified)
`backend/server.py` `startup_db()` continues past index creation into a full migration over **every** product:

```python
products = await db.products.find({}, {"_id": 0}).to_list(10000)
for p in products:
    await ensure_warehouse_stock(p["id"])          # 1 find(warehouses) + 3× find_one  ≈ 4 round-trips
    all_wh_stock = await db.warehouse_stock.find({"product_id": p["id"]}).to_list(10)  # 1
    ... (conditional updates)                       # 0–2
    await recalculate_product_stock(p["id"])        # find_one + find + 3× find_one(wh) + update ≈ 6
# then:
all_wh_stocks = await db.warehouse_stock.find({}, {"_id": 0}).to_list(100000)
for s in all_wh_stocks:                             # cleanup loop
    if s["product_id"] not in product_ids:
        await db.warehouse_stock.delete_many(...)
```

Production data counts (queried live against the deployed Atlas DB `partial-payment-dev-test_database`):
- `products`: **887**
- `warehouse_stock`: **2,661**

That is ~11 **sequential awaited** Atlas round-trips per product × 887 ≈ **~9,700 serial round-trips**, plus a 2,661-row cleanup pass. At typical Atlas round-trip latency (~15–30 ms) this is **~150–300+ s**, well beyond the ~120 s readiness window.

## Why it passed in preview / earlier deploys
Preview runs against **local Mongo (localhost, sub-millisecond)** so the same loop finishes in time. On the managed Atlas production DB the per-op network latency multiplies across thousands of serial ops and blows the readiness budget. The data set has also grown since the last successful deploy (2026-08-27).

## Reproduction status
**Diagnosed, not reproduced in sandbox.** The eph sandbox has no production Atlas credentials and no prod-scale data/latency, so the timeout cannot be reproduced there. Root cause is established from the pod logs, the source, and live row counts above.

## Fix (owner: E1 / code — `backend/server.py`)
Get the heavy migration OFF the startup critical path so uvicorn binds the port immediately. Keep the cheap seeding (admin user + 3 warehouses) inline; move the per-product migration and the orphan-cleanup loop into a background task:

```python
import asyncio

@app.on_event("startup")
async def startup_db():
    try:
        from storage import init_storage
        init_storage()
        logger.info("Emergent object storage initialized")
    except Exception as e:
        logger.warning(f"Object storage init failed: {e}")

    await create_indexes()

    # cheap seeding — safe to keep inline
    admin_exists = await db.users.find_one({"role": "admin"})
    if not admin_exists:
        ...  # unchanged
    wh_count = await db.warehouses.count_documents({})
    if wh_count == 0:
        ...  # unchanged

    # heavy migration -> background, so the port opens now
    asyncio.create_task(_migrate_products_background())

async def _migrate_products_background():
    try:
        products = await db.products.find({}, {"_id": 0}).to_list(10000)
        ...  # the existing per-product loop + orphan cleanup, unchanged
        logger.info("Product/warehouse migration complete")
    except Exception as e:
        logger.exception(f"Background migration failed: {e}")
```

Stronger follow-ups (recommended, not required to unblock the deploy):
- Make the migration a **one-off** gated by a marker doc (e.g. a `migrations` collection) so it doesn't re-run on every boot.
- **Batch** the work: pull all warehouses once, bulk-upsert missing `warehouse_stock` with `bulk_write`, and compute totals with an aggregation instead of N sequential `find_one`/`update_one` calls.
